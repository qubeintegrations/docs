See the [API Reference](/api-reference) for full documentation of all 261 QuickBooks operations and their REST(ish) endpoints, and even try them from right here in the docs. Better yet, use the [MCP server](/mcp-server) to let your agent build and validate any request.

Every QuickBooks operation is a REST endpoint under a connection, covering lists
(customers, vendors, items, accounts), transactions (invoices, bills, payments, sales receipts, journal
entries), payroll and reports. They are all compiled and validated directly from QuickBooks' own schema definitions, so they support
every feature native qbXML offers. All behave the same way:

<Steps>
  <Step title="Send JSON">
    You send JSON to `https://qubesync.com/api/v2/connections/{connection_id}/{resource}`.
  </Step>
  <Step title="Save the queued request's ID">
    Your request is validated against QuickBooks' schema. A valid request is queued, and you get `201 Created` with the queued request.
  </Step>
  <Step title="Receive the answer">
    When the Web Connector next checks in, QuickBooks runs it and the answer is POSTed to your
    `webhook_url` as JSON.
  </Step>
</Steps>

## The pattern

| You want to | Method | Example | QuickBooks request |
| --- | --- | --- | --- |
| List or search | `GET` | `GET /connections/{id}/customers?name_starts_with=River` | `CustomerQueryRq` |
| Create | `POST` | `POST /connections/{id}/invoices` | `InvoiceAddRq` |
| Update | `PUT` | `PUT /connections/{id}/customers` | `CustomerModRq` |
| Delete | `DELETE` | `DELETE /connections/{id}/lists` | `ListDelRq` |
| Do something else | `POST` | `POST /connections/{id}/txn-void` | `TxnVoidRq` |

Fields are snake_case versions of QuickBooks' own names (`ListID` becomes `list_id`, `EditSequence` becomes
`edit_sequence`), in the request body and in the answer.

Add `webhook_url` as a **query parameter** to every call, whatever the method. That's where the answer
goes.

## A small API client

Every example here uses the same few lines: JSON in, the response's `data` out.

<CodeGroup>
```ruby Ruby
require "net/http"
require "json"

module Qube
  def self.api(method, path, body = nil, query: {})
    uri = URI("https://qubesync.com/api/v2#{path}")
    uri.query = URI.encode_www_form(query) if query.any?

    req = Net::HTTP.const_get(method.to_s.capitalize).new(uri, "Content-Type" => "application/json")
    req.basic_auth(ENV.fetch("QUBE_API_KEY"), "")
    req.body = body.to_json if body

    res = Net::HTTP.start(uri.host, uri.port, use_ssl: true) { |http| http.request(req) }
    raise "QuBe Sync answered #{res.code}: #{res.body}" unless res.is_a?(Net::HTTPSuccess)

    JSON.parse(res.body).fetch("data")
  end
end
```

```javascript Node.js
const AUTH = "Basic " + Buffer.from(`${process.env.QUBE_API_KEY}:`).toString("base64");

async function qube(method, path, body, query = {}) {
  const url = new URL(`https://qubesync.com/api/v2${path}`);
  Object.entries(query).forEach(([k, v]) => url.searchParams.set(k, v));

  const res = await fetch(url, {
    method,
    headers: { Authorization: AUTH, "Content-Type": "application/json" },
    body: body ? JSON.stringify(body) : undefined,
  });
  if (!res.ok) throw new Error(`QuBe Sync answered ${res.status}: ${await res.text()}`);
  return res.json();
}
```

```python Python
import os
import requests

def qube(method, path, body=None, **query):
    res = requests.request(method, f"https://qubesync.com/api/v2{path}",
                           auth=(os.environ["QUBE_API_KEY"], ""), json=body, params=query)
    res.raise_for_status()
    return res.json()["data"]
```
</CodeGroup>

## Query

Filters are query parameters. Each resource has QuickBooks' own filters, such as names, modified dates,
active status and reference numbers:

<Request
  path="/api/v2/connections/{connection_id}/customers"
  query={{
    active_status: "ActiveOnly",
    name_starts_with: "River",
    max_returned: 25,
    webhook_url: "https://your-app.example/webhooks/qube",
  }}
/>

```http
GET /api/v2/connections/{connection_id}/customers?active_status=ActiveOnly&name_starts_with=River&max_returned=25&webhook_url=https://your-app.example/webhooks/qube
```

```bash
curl -u "$QUBE_API_KEY:" \
  -G \
  "https://qubesync.com/api/v2/connections/$CONN_ID/customers" \
  --data-urlencode "active_status=ActiveOnly" \
  --data-urlencode "name_starts_with=River" \
  --data-urlencode "max_returned=25" \
  --data-urlencode "webhook_url=https://your-app.example/webhooks/qube"
```

</Visibility>
{/* agent-block:end */}

A query's answer is always a **list** in `response_json.data`, even when one record or none matches. A list
query QuickBooks pages arrives a page at a time, each page as its own webhook, unless you look records up by
id or name or send `max_returned` alone. See [Pagination](/pagination).

<Tip>
  Ask only for what changed, so a full import becomes a cheap incremental sync. The two kinds of query
  take the modified dates differently.

  A **list** query (`customers`, `vendors`, `items`...) takes `from_modified_date` and `to_modified_date`
  as plain query parameters.

  A **transaction** query (`invoices`, `bills`, `payments`...) takes them inside
  `modified_date_range_filter`.

  You can find full set of options in the [API Reference](/api-reference), or use the [MCP](/mcp-server) to build and validate requests.
</Tip>

Date fields take `YYYY-MM-DD`. Datetime fields take ISO 8601, such as `2026-09-03T17:28:28`, with an
optional offset such as `+00:00`. A trailing `Z` is accepted and sent to QuickBooks as `+00:00`. A value in
any other shape is refused with `400` when you queue the request.

A filter that takes several values, such as `ref_number`, `list_id` or `txn_id`, is an array. Repeat the key
(`ref_number=1001&ref_number=1002`) or use brackets (`ref_number[]=1001&ref_number[]=1002`); either asks for
every value you list. A comma doesn't separate values: `ref_number=1001,1002` looks for the one number
`1001,1002`. A filter that takes a single value, such as `max_returned`, can't be repeated, and the request
is refused with `400`.

A create's answer is the **new record** in `response_json.data`, with the ids QuickBooks gave it:

```json response_json (abridged)
{
  "status": "success",
  "data": {
    "txn_id": "1-1790470623",
    "ref_number": "1001",
    "txn_date": "2026-09-27",
    "due_date": "2026-10-27",
    "customer_ref": { "list_id": "8000001F-1790470623", "full_name": "Riverbend Electric" },
    "subtotal": 530.0,
    "balance_remaining": 530.0,
    "is_paid": false,
    "edit_sequence": "1790470623",
    "invoice_line_ret": [
      { "txn_line_id": "1L-1790470623", "item_ref": { "full_name": "Consulting" }, "desc": "Consulting services (hourly)", "quantity": 3.0, "rate": 150.0, "amount": 450.0 },
      { "txn_line_id": "2L-1790470623", "item_ref": { "full_name": "Widget" }, "desc": "Standard widget", "quantity": 2.0, "rate": 40.0, "amount": 80.0 }
    ]
  }
}
```

Store the `list_id` or `txn_id` against your own record. A `list_id` is stable for the life of the company
file; a `full_name` changes when someone renames the record in QuickBooks.

Keep it with the connection it came from. QuickBooks makes a `list_id` unique only within one list of one
company file, and a `txn_id` within one transaction type: two of your customers' files can hold the same one,
and a copy of a file (a restored backup, a test copy) holds every one the same. So when your app keeps its
own table of QuickBooks records, find each row by the connection, the kind and the id together: never by the
id alone, and not by your customer's account either, since a customer who connects another company file gets a
new connection.

If QuickBooks saved the record but left something out, such as a field this QuickBooks doesn't support, the
answer is still a success, with `response_json.warning` saying what. See
[Warnings](/error_handling#quickbooks-said-yes-with-a-warning).

<Warning>
  Names are unique across QuickBooks' customer, vendor, employee and other-name lists together. Creating a
  customer whose name a vendor already has fails with error 3100 (`name_in_use`). Plan for it: the
  [`ensure`](/workflows#pick-a-template) workflow handles it for you.
</Warning>

## Update

QuickBooks uses optimistic locking. Send the record's `list_id` (or `txn_id`) with the `edit_sequence` you
last read, and preferably only the fields you're changing:

    edit_sequence: "1790470623",
    phone: "512-555-0100",

The answer is the updated record, with a **new** `edit_sequence`. If the record changed in QuickBooks since
you read it, the update is refused with error 3200 (`stale_edit_sequence`): query the record again and
retry with the fresh `edit_sequence`, or let your user decide how to manage conflicts. A [workflow](/workflows) like `upsert` can handle this for you.

## Requests are pre-validated

QuBe Sync validates every request against QuickBooks' schema before queuing it, so a typo fails in your
test suite, not on your customer's PC. You get `400` and nothing is queued:

```json 400 Bad Request
{ "errors": "unknown parameter: \"emial\"" }
```

```json 400 Bad Request
{ "errors": "active_status: must be one of [:all, :active_only, :inactive_only], got \"Sometimes\"" }
```

## Ordering, dependencies and retries

| How it works | What to do |
| --- | --- |
| **Requests run in the order you queued them**, one connection at a time. | Queue a request that depends on another (an invoice for a customer you're creating) **from the first one's webhook**, not alongside it. Or let a [workflow](/workflows) run the sequence for you. |
| **Every call queues a new request.** If your app sends the same call twice, QuickBooks runs it twice: two calls to create an invoice make two invoices. QuBe Sync itself never resends a request QuickBooks might have received. It only retries a request the Web Connector couldn't deliver at all. | **Retry with an idempotency key.** Send an `Idempotency-Key` header with each call, and a call you send again after a timeout queues nothing new (see [Retrying a call safely](#retrying-a-call-safely)). |
| **QuBe Sync is already retrying** a request that's <Badge color="orange">`retryable`</Badge>. | **Don't resend it.** See [Error handling](/error_handling). |

### Retrying a call safely

A timeout or a dropped connection can leave your app without the `201`, and so without the request's `id`,
though the request was queued. Send an `Idempotency-Key` header with each call, and send a call whose answer
you never got again with the same key:

```bash
curl -u "$QUBE_API_KEY:" \
  -X POST "https://qubesync.com/api/v2/connections/$CONN_ID/customers?webhook_url=https://your-app.example/webhooks/qube" \
  -H "Idempotency-Key: 4c1f0b9e-7d2a-4b8e-9f3a-1e6d5c2b7a90" \
  -H "Content-Type: application/json" \
  -d '{"name": "Acme Co"}'
```

<ParamField header="Idempotency-Key" type="string">
  1 to 255 printable ASCII characters. Every operation, [queueing qbXML](#sending-qbxml-yourself) and
  [starting a workflow run](/workflows) take one. Other calls ignore the header.

  A key belongs to your app, so your sandbox and production apps never share one. It lasts as long as the
  request or run it created.
</ParamField>

| You send | What happens |
| --- | --- |
| The same key with the same call (method, path, query and body) | `201` with the request the first call queued, as it is now, and the header `Idempotent-Replayed: true`. Nothing new is queued, and no extra webhook goes out. |
| The same key with a different call | `422` naming the header. A key stands for one request: generate a new one (a UUID) for each request you mean to make once, and store it with your record before you send it. |
| A call that's refused | `400`, `404` or `422`. It queues nothing and uses up no key: fix it and send it again with the same key. |

The key covers a lost `201` from QuBe Sync, not a lost answer from QuickBooks. A request that ends
<Badge color="purple">`timed_out`</Badge> was queued and sent, so sending it again with its key only returns it. See
[When the answer is lost](/error_handling#when-the-answer-is-lost).

## Sending qbXML yourself

When no operation expresses the request you need, you already have the qbXML (from an older integration,
or from Intuit's own examples), or you want QuickBooks to run several requests together, [queue the qbXML](/api-reference/v2/queued-requests/queue-a-qbxml-request)
as it is:

<Request
  method="POST"
  path="/api/v2/connections/{connection_id}/queued-requests"
  query={{ webhook_url: "https://your-app.example/webhooks/qube" }}
  body={{
    request_xml:
      '<?xml version="1.0" encoding="utf-8"?><?qbxml version="16.0"?><QBXML><QBXMLMsgsRq onError="stopOnError"><CustomerQueryRq requestID="1"><MaxReturned>10</MaxReturned></CustomerQueryRq></QBXMLMsgsRq></QBXML>',
  }}
/>

{/* agent-block:start */}

```bash
  }'
```

</Visibility>
{/* agent-block:end */}

<ParamField body="request_xml" type="string" required>
  The whole qbXML document, sent to QuickBooks as it is. It's checked before anything is queued:

  1. It has no DOCTYPE. qbXML doesn't use one.
  2. It declares its qbXML version, such as `<?qbxml version="16.0"?>`, and the version is 13.0, 14.0,
     15.0 or 16.0.
  3. It is valid against that version's qbXML schema.
  4. `<QBXML>` holds only `<QBXMLMsgsRq>`, with at least one request inside it.
  5. In a batch (two or more requests), no request has an `iterator` attribute. Queue an iterator query
     on its own.
  6. `onError` is `stopOnError` or `continueOnError`. QuickBooks Desktop refuses `rollbackOnError` for
     the whole envelope.

  If it breaks one, nothing is queued and the answer is `422`, with `errors.request_xml` saying which:

  ```json 422 Unprocessable Entity
  { "errors": { "request_xml": ["CustomerQueryRq has an iterator: queue an iterator query on its own, not in a batch"] } }
  ```

  Write every amount with its two decimals: `<TotalAmount>40.00</TotalAmount>`, not `40`. The schema
  allows `40`, so it passes these checks, but QuickBooks refuses it with `3040` when it runs the request.
  Quantities and rates can be whole numbers. The operations write amounts this way for you.
</ParamField>

<ParamField query="webhook_url" type="string">
  Where the answer goes. It stays in the query string, as on every other call.
</ParamField>

The answer arrives at your `webhook_url` like any other request. qbXML you send yourself is sent as you wrote
it, so it isn't [paged](/pagination) for you. To page a single query, give it `iterator="Start"` and a
`MaxReturned` page size, and you get one webhook per page of results.

The `201` carries `warnings` beside `data`, a list that is empty when there's nothing to say. A query
QuickBooks pages that has neither an `iterator` nor `MaxReturned`, and doesn't look records up by id or
name, gets an `unpaged_query` warning: QuickBooks will answer it with every match at once, and one answer
over the [size limit](/error_handling#when-the-answer-is-too-large) isn't kept. Warnings are only in that
`201`; `links.self` doesn't return them.

### A batch

Put several requests in one `<QBXMLMsgsRq>` and QuickBooks runs them in order, in one go. `response_json`
then lists every request's outcome, in the order you sent them:

```json response_json for a batch (abridged)
{
  "status": "error",
  "responses": [
    { "request": "CustomerAddRq", "request_id": "1", "status": "success",
      "data": { "list_id": "80000021-1790470623", "full_name": "Lakeside Dental" } },
    { "request": "ItemServiceAddRq", "request_id": "2", "status": "error",
      "error": { "code": 3100, "type": "name_in_use", "message": "The name \"Consulting\" of the list element is already in use." } },
    { "request": "InvoiceAddRq", "request_id": "3", "status": "not_processed" }
  ]
}
```

<Visibility for="agents">
Each entry has `request` (the request's name), `request_id` (its `requestID`, or `null`) and `status`. A
request QuickBooks ran or refused is `success` or `error`, with the same `data`, `message`, `warning` or
`error` as a single request's summary. `not_processed` is a request QuickBooks skipped: with
`onError="stopOnError"` it stops at the first request that fails and answers each one after it "The
request has not been processed." (status 3231), so those are `not_processed`. With
`onError="continueOnError"` it carries on and runs each one. A 3231 that doesn't follow an earlier failure
is QuickBooks declining that request itself, because the company file's edition or preferences don't
allow it, so it's an `error`. The top-level `status` is `success` only when every entry is.

A batch QuickBooks answered is <Badge color="green">`response_received`</Badge>, whatever its entries say, because some of its requests
may have gone through: in the example above, the customer was added. Look at the entries to see what
happened to each request, and don't resend the batch. Queue again only the requests that need it. 
</Visibility>
