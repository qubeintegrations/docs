`qube` puts your QuBe Sync account in your terminal. It's the quickest way to set up a development
environment, and the safest way to let an AI coding agent work against your account: the agent can do
everything below without ever seeing a secret.

<Note>
  Some of this page needs v0.3.0 or later of the CLI: `qube connections create ... --use`,
  `qube use --connection` (the default connection they set), `qube qb RESOURCE create --example`,
  and `qube workflows install --replace`. Run `qube version` to see what you have, and
  `brew upgrade qube` to update. On v0.2.0, pass the connection to each command and write request
  bodies yourself.
</Note>

## Install

<CodeGroup>
```bash Homebrew
brew install qubeintegrations/tap/qube
```

```bash Go
go install github.com/qubeintegrations/qube-cli/cmd/qube@latest   # Go 1.16 or newer
```
</CodeGroup>

Or download the archive for macOS, Linux or Windows (amd64 and arm64) from the
[releases page](https://github.com/qubeintegrations/qube-cli/releases), unpack it, and put `qube` on your
`PATH`. `qube version` prints what you have; `eval "$(qube completion zsh)"` (or `bash`, `fish`) adds tab
completion.

## Log in

```bash
qube login
```

`qube login` shows a short code and opens the dashboard. You confirm the code there, signed in as yourself,
and choose what the session may reach (**sandbox apps only** by default) and whether it may change anything
(**read and write**, or **read-only**). The terminal then receives a session token, stored in your config
directory with owner-only permissions. Nothing is typed into the terminal and nothing is pasted into a chat.

`qube login --read-only` asks for a read-only session: the approval page preselects it. See
[Sessions, scope and access](#sessions-scope-and-access).

`qube status` shows which host, user and app the CLI is pointed at, and when the session expires, without a
network call. `qube whoami` asks the server to confirm it.

## Set up a project in three commands

```bash
qube use "My App Dev"                                     # the app the commands below act as
qube env --write .env                                     # QUBE_URL, QUBE_API_KEY, QUBE_WEBHOOK_SECRET
qube connections create --simulated --name "Local dev" --use   # a fake QuickBooks, connected at once
```

`qube env --write` names the variables it wrote and prints nothing of their values. `qube env --print`
prints them in full as `export` lines, if you want to see them.

If the file already exists, `--write` changes only its `QUBE_*` lines: those already there are updated in
place, keeping any `export` in front, the missing ones are added at the end, and every other line stays
as it was. If `.env` is a symbolic link, the file it points to is the one updated.

`--use` makes the new connection the default, so commands that act on a connection don't need its id:

```bash
qube qb customers list --max-returned 5 --wait    # on "Local dev"
qube requests list --state error
qube use --connection Riverbend                   # switch, by id or name; `none` forgets it
qube requests list --connection <id>              # another connection, this once
```

`qube connections list` marks the default with `*`. Deleting a connection always needs it named.

## Commands

<AccordionGroup>
  <Accordion title="Apps and sessions" icon="key">
    ```bash
    qube apps                       # the apps this session may act on
    qube use "My App Dev"           # the default app
    qube sessions                   # your CLI sessions on this host
    qube sessions revoke <id>       # end one
    qube logout                     # end this one
    ```
  </Accordion>
  <Accordion title="Connections and requests" icon="plug">
    ```bash
    qube connections list
    qube connections create --simulated --name "Local dev"
    qube connections create --name "Riverbend" --redirect-url https://your-app.example/qb/callback
    qube connections show <connection>
    qube connections update <connection> --name "Riverbend Electric"
    qube connections onboarding-url <connection>              # a fresh link; the old one stops working
    qube connections qwc <connection> --output riverbend.qwc  # the file the Web Connector adds
    qube connections password <connection>                    # a new Web Connector password
    qube connections delete <connection>                      # asks first; --yes in a script
    qube connections name-index <connection> --webhook-url https://your-app.example/webhooks/qube   # build it before the first match
    qube match <connection> customer "ACME, Inc." --email ap@acme.example   # the records a name could mean
    qube match <connection> item Consulting --exact-only      # exact or none, never a fuzzy match
    qube requests list <connection> --state error --page-size 50   # 20 per page by default
    qube requests show <connection> <id>                      # one request, as JSON
    qube requests pages <connection> <id>                     # every page of an iterated query
    qube requests tail <connection>                           # watch requests as they're answered
    qube requests discard <connection> <id>                   # withdraw one the Web Connector hasn't taken
    ```
    `qube match` asks a realtime or simulated connection's name index which records a name could mean
    ([Match names](/matching)). A customer, vendor, employee or other name can be matched on more than
    its name: `--account-number`, `--email`, `--phone` and `--postal-code` can make a strong match, and
    `--city` and `--company-name` rank the candidates. `--parent` matches under a parent (a job under a
    customer), and `qube match -h` lists the kinds and flags. The first match on a connection starts
    building its index and is refused until it's in (exit `1`); `qube connections name-index` starts the
    build ahead of time, and `--webhook-url` is told when it's ready.
  </Accordion>
  <Accordion title="QuickBooks operations" icon="book">
    ```bash
    qube qb                                                   # every resource and its verbs
    qube qb customers                                         # one resource's operations
    qube qb customers list --help                             # its flags, their rules, an example
    qube qb customers list <connection> --name-starts-with North --max-returned 5 --wait
    qube qb customers create <connection> --name "Northwind Builders" --bill-address '{"city": "Austin"}'
    qube qb invoices create --example > invoice.json          # the API's example body, to edit
    qube qb invoices create <connection> --data @invoice.json
    qube qb txn-void execute <connection> --txn-id 1A2B-3C --txn-void-type Invoice
    qube qb items list <connection> --wait    # every page, 100 items at a time
    ```
    `qube qb` runs every QuickBooks operation in the [API reference](/api-reference/introduction). It
    reads them from the API's own OpenAPI document, so the CLI offers the flags and body fields your
    host has. Query parameters and the body's top-level fields are flags (`max_returned` is
    `--max-returned`), and `--data` takes a whole body as JSON, `@file` or `-` for standard input.
    Each operation queues a request. `--wait` waits for QuickBooks' answer and prints it, every page
    of an iterated query, and exits `1` if it failed. It waits up to 10 minutes; use `--wait=30m` for
    longer. Otherwise pass `--webhook-url` to be sent the answer, or look it up later with
    `qube requests show`. `--help --json` prints an operation's full parameters and body schema.

    `--help` comes from the same document. Flags that exclude each other are listed together in an
    `Exactly one of:` block (or `At most one of:` when none is required), with `or:` between the
    alternatives and the flags that go together grouped under each. Help also shows which lists
    combine (an invoice's item and group lines, a journal entry's debit and credit lines), and which
    keys of an object are required. Help ends
    with an example built from the operation's request example in the
    [API reference](/api-reference/introduction), and `--example` prints that body as JSON for you
    to edit and send with `--data @file`. Tab completion offers each operation's flags, and the
    values of a flag that has a fixed list.
  </Accordion>
  <Accordion title="The simulator" icon="flask">
    ```bash
    qube simulator show <connection>                  # the fake company file and its faults
    qube simulator faults <connection> --next 3100    # one-shot: xml | 3100 | 3120 | 3140 | 3180 | 3200 | ok
    qube simulator faults <connection> --next lost    # one-shot: applied, then its answer is lost; --next ok clears it
    qube simulator faults <connection> --qb closed    # sticky: closed | modal | mismatch | unexpected | ok
    qube simulator faults <connection> --latency 5000 # milliseconds QuickBooks "thinks" per answer
    qube simulator sync <connection>                  # run the fake Web Connector now
    qube simulator reset <connection>                 # back to the seeded company, faults cleared
    ```
    See [Test without QuickBooks](/simulator).
  </Accordion>
  <Accordion title="Workflows" icon="diagram-project">
    ```bash
    qube workflows templates                        # the shipped templates
    qube workflows install add_transaction --publish   # --as NEW_KEY installs a second copy
    qube workflows list                             # TEMPLATE: the template each came from, and whether it changed since
    qube workflows show add_transaction
    qube workflows validate ./chart.json            # check a chart without saving it; whether what it calls exists is checked on push
    qube workflows push ./chart.json --publish --notes "Handle vendors too"   # saved under the chart's top-level "key", which it must have
    qube workflows publish add_transaction --notes "Handle vendors too"
    qube workflows versions add_transaction
    qube workflows usage add_transaction                 # how to call it, as Markdown
    qube workflows schema                           # the chart JSON Schema
    qube workflows run add_transaction --connection <id> --input @order.json \
      --wait                                        # until it ends or needs a decision; --version published|working|N on sandbox
    qube workflows runs <connection>                # runs on a connection
    qube workflows runs <connection> <run> --events # one run's event log; --after SEQ for the next page
    qube workflows decide <connection> <run> rename --data '{"name": "Lone Star Supply Co (customer)"}'
    qube workflows cancel <connection> <run> --reason "Wrong customer"
    qube workflows delete-run <connection> <run>    # an ended run and its history
    qube workflows unpublish add_transaction
    qube workflows delete add_transaction
    ```
    If the app already has a workflow at that key, the install is refused with `409` (`key_taken`), and so
    is a second `POST /workflow-templates/{key}/install`. `--replace` (`"replace": true` in the API)
    installs again over it: the workflow, and each one it calls that the app already has, gets the
    template's current chart, earlier versions kept, so a setup script can run the same install every
    time. `--as` (`as` in the API) installs a second copy under another key instead, and
    `qube workflows push` replaces a workflow with a chart file of your own.

    A template can change after you install it. `qube workflows list` then says `update available` in
    its TEMPLATE column (`update available (edited)` when you've changed the workflow too), and prints
    the `install --replace` command that takes the current version. For an edited workflow that command
    replaces your edits.

    See [Workflows](/workflows).
  </Accordion>
  <Accordion title="Anything else" icon="code">
    ```bash
    qube api GET "/connections/<id>/customers?max_returned=5"
    qube api POST /connections/<id>/customers --data '{"name": "Northwind Builders"}'
    qube api PUT /connections/<id>/customers --data @update.json
    ```
    `qube api` calls any v2 path with the current app's key. A path that doesn't start with `/api/` is
    a v2 path. `--data` takes JSON, `@file` or `-` for standard input.
  </Accordion>
</AccordionGroup>

`qube help` lists every command and flag. Every command also takes:

| Flag | |
| --- | --- |
| `--json` | Machine-readable output. |
| `--app` | Act as a specific app, this once. |
| `--connection` | The connection to act on, this once, when a command doesn't name one. |
| `--timeout` | Seconds (or `2m`). Default 60. |
| `--yes` | Answer yes to a confirmation, for scripts. See [Production apps](#production-apps). |

Exit codes: `0` ok, `1` the command failed, `2` wrong usage, `130` interrupted.

<Note>
  `--wait` and `qube requests tail` poll, so you can see answers from a terminal or a script. They're a
  developer convenience. Your integration should pass a `webhook_url` with every request and be told
  when it's answered ([Webhooks](/webhooks)).
</Note>

## Receive webhooks locally

`qube listen` gives you a `webhook_url` that reaches the app on your laptop, with no tunnel. It works for
sandbox apps:

```bash
qube listen --forward-to http://localhost:3000/webhooks/qube --write-env .env
```

```
Webhook URL for My App Dev (the same every time on this machine):
  https://qubesync.com/relay/rl_4f7k2m9q8t3w6x1z5c0v7b2n4h
Forwarding to http://localhost:3000/webhooks/qube. Ctrl-C to stop.
14:02:11  request 1f0c2a3b…  response_received  → POST /webhooks/qube  200  41 ms
14:02:19  workflow_run.notification  customers_page #3  → POST /webhooks/qube  200  58 ms
14:03:02  request 1f0c2a3b…  response_received  → POST /webhooks/qube  500  12 ms  (QuBe will retry)
```

Pass the URL it prints as the `webhook_url` of your requests and workflow runs, and every delivery to it
is sent on to the `--forward-to` URL: the body and `X-QUBE-Signature` byte for byte, so your app
[verifies the signature](/webhooks#securing-your-endpoints) as it will in production. A path or query you
add to the URL is added to the `--forward-to` URL too. Your app's answer is the delivery's outcome, so a
non-`2xx` is retried and the dashboard shows each attempt, as for any `webhook_url`.

| Flag | |
| --- | --- |
| `--forward-to URL` | Required. Where deliveries go; `localhost:3000` means `http://localhost:3000`. |
| `--write-env FILE` | Writes the URL into `FILE` as `QUBE_WEBHOOK_URL`, changing no other line. Without it, `qube listen` prints the line to add when `./.env` lacks it. |
| `--forget` | Asks, then deletes this machine's URL for the app, so the next `qube listen` gets a new one. With `--forward-to`, it then listens on the new URL. |
| `--json` | One JSON line with the app and URL, then one per delivery: `at`, `ms`, `path`, `summary`, and `status` or `error`. |

- **One URL per machine.** The URL stays the same for an app on this machine, so it goes into `.env` once.
  The machine is identified by a random id in the CLI's config folder, shared by every config on it. You can
  have URLs on up to 10 machines per app; an 11th takes over the one unused longest, which then stops
  working, and `qube listen` says so.
- **One listener per URL.** Starting `qube listen` again, in another terminal, takes over: the older one stops
  and says why.
- **When it isn't running,** deliveries fail and are retried a few times like any other, and **Resend
  webhook** in the dashboard sends one again. It reconnects by itself when the network drops.
- Ctrl-C stops it (exit `130`).

See [Receive webhooks in development](/ngrok) for a tunnel instead.

## Production apps

In a production app, every request that changes something asks before it's sent, and names the app.
That covers every `qube qb` operation except `list`, since each one writes to the customer's real
company file. It also covers creating or changing a connection (its password, onboarding link and
name index too), discarding a request, driving the simulator, every workflow change, run or answer, and
`qube api` with any method but `GET`. Reads never ask. Removing something (a connection, a workflow,
a run, a `qube listen` URL) asks in any app.

A script answers with `--yes`. Without a terminal, or under `--json`, a request that would ask is refused
until `--yes` is given, so nothing reaches a production company file by accident.

## Let an AI agent use it

Log in yourself, choosing the default **sandbox** scope, then let your coding agent run `qube`. It can
write your `.env`, create simulated connections, inject faults, push workflows and call the API, but it
never sees the session token or your production apps, and you can revoke its access at any moment. For
an agent that should only look (reading your data, running QuickBooks queries, checking charts), approve
a **read-only** session instead: the server refuses anything else.
Combined with the [MCP server](/mcp-server), an agent can explore QuickBooks operations, build requests
and test them end to end on its own.

## Sessions, scope and access

A session belongs to you, in one organization.

| Approved with | It can | It can't |
| --- | --- | --- |
| **Sandbox** scope (the default) | List the organization's sandbox apps, read their API keys and webhook secrets, and act on their connections. | See production apps, or change billing, members or your account. |
| **Every app** scope | The same, in production apps too. | Change billing, members or your account. |
| **Read-only** access | List and show what its scope reaches, run QuickBooks queries, [match names](/matching), validate charts, download a connection's QWC file and [receive webhooks](#receive-webhooks-locally) with `qube listen`. | Create, change, delete, discard, run or answer anything, or read an app's API key or webhook secret, so `qube env` isn't available to it. |

The server enforces read-only access. `qube status` and `qube sessions` show each session's access.

Sessions expire after 30 days. `qube logout`, `qube sessions revoke <id>`, or **CLI sessions** in the
dashboard end one sooner, and the CLI stops working at once: it calls the API with the session's own
token, never the app's API key. The token is only ever sent to `qubesync.com`, the host that issued it.
